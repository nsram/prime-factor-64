## 2. Invariants and independent oracles

### Mathematical

- Build a reviewed fixture independently of both production deck builders. Enumerate distinct ascending pairs from 3 through 19, excluding 10, whose product is strictly above 100. Add the eight square cards for 11 and 13 through 19, plus 17 × 21 = 357. Cross-check against the published 64-result table and the guide. Expect 64 distinct products, 68 unordered permitted pairs, and 200 legal practice IDs across both pair-based directions and result-based factor recall.
- The only products with two permitted factorizations are 108 (6 × 18, 9 × 12), 112 (7 × 16, 8 × 14), 126 (7 × 18, 9 × 14), and 144 (8 × 18, 9 × 16). The first pair in each row is the Easy teaching pair. Twelve squared is an anchor in the guide. It is outside the deck's allowed pairs even though 144 is a card result. Both games must agree with the independent fixture.
- In a deal, every fact has an eligible expression. Each board or round contains unique products, a full session covers the fixture exactly once, and a short session has the requested count with no repeats. At the UI, visible cards on the two sides represent the same eligible set for that board or reveal wave.
- The Easy oracle comes from the approved board table, copied as reviewed test data with its provenance. It specifies exact membership, labels, wrap order, splits at size 4, and two named sections of eight at size 16. The strategy counts are 8 Squares, 8 Next Door, 24 Straddle, and 24 Split at 10. Independently check equal factors, consecutive factors, an integer midpoint with the difference-of-squares identity, and splitting a teen factor at 10, respectively. These mathematical predicates can overlap. The approved assignment decides membership.
- Classic and Fog Sweep use same-ending groups. Exact Classic template inventories are characterization tests. Compare observed last-digit counts against a feasible grouping, allowing multiple same-ending groups to merge in the visible histogram. Fog Sweep's opening eight facts can be partitioned into same-ending groups of size two or three. Every subsequent deal wave has two distinct products sharing a last digit.

### Behavioral and persistence

- A wrong guess affects the fact selected first. A correct match changes progress once, disables or clears both cards, and cannot be counted again. A selection can originate on either side. A cross-section click in Easy switches selection without a miss. Successful Easy matches move to aligned rows within their own section and retain that section's match order.
- Classic elapsed time excludes pauses and recall. Fog Sweep measures first accepted tap to last match, excluding pauses, and sums the displayed round times for the final result. Easy is untimed. Review preserves Fog Sweep's expression positions. Easy replay discards only the current board's previous score, misses, and recall counts.
- Weak facts are prompt-specific. Retirement requires two unaided correct recall answers on separate local calendar days, both after the latest applicable miss. Same-day repeats, matching successes, and answers before or at a newer miss do not advance retirement. A later miss reopens the prompt. Weak Facts presents at most eight prompts, at most five weak prompts, and at most one prompt per product in a drill.
- A staged valid observation must survive navigation, waiting behind a lock, and replay after a successful main write with unfinished cleanup, assuming the origin's storage remains available. When two tabs save distinct observations with Web Locks, retain both. On a shared fact, merge the latest seen and miss timestamps and keep at most the two latest distinct qualifying days. Best first-try score takes the maximum, fastest perfect time the minimum, and completed-run IDs are unique. Compare semantics independently of JSON key order and run-ID insertion order.
- Practice backup merge, reset, corrupt-record recovery, and fallback are different operations. A rejected import leaves good progress intact. A recoverable corrupt snapshot is copied before removal. An outbox entry is removed only after successful main persistence, or as part of an explicit reset. An unavailable store should degrade without blocking play. Concurrent fallback without Web Locks needs its own characterization and no implied lock-equivalent guarantee.

## 4. Lightweight tooling and implementation map

- **Node LTS with `node:test` and `node:assert/strict`** for independent fixture checks and deterministic tests of the shared store public API. Use a fresh VM and a small Storage/Web Locks adapter for controllable failures. The adapter must model key enumeration and failure boundaries and must be cross-checked against the real browser tests. Use a reviewed set of fixed seeds with failure messages that print seed and configuration. Generate valid histories and test merge laws. Start with no property-testing dependency. Add one later only if it provides useful shrinking or broader generated cases. [Node test runner](https://nodejs.org/api/test.html)
- **Playwright Test with Chromium** for real game pages, navigation, keyboard/touch, downloads, context isolation, and native Web Locks across tabs. Use one narrow dealer probe in a browser realm to query existing top-level pure functions and their outputs. Keep live production code as the source under test. Avoid copying inline function bodies into the tests or adding production test-only exports. Use stable accessible locators and structure assertions. Use a test audio stub for cue routing and real audio only in manual checks. [Playwright installation](https://playwright.dev/docs/intro)
- **Separate time, randomness, and concurrency.** Install a controlled Playwright clock before navigation for timer-boundary tests. Use a fixed timezone such as America/New_York and explicit local dates for retirement. The clock affects the browser context, so a shared-clock multi-tab case must not pretend its pages have separate clocks. Hold and release native locks with explicit barriers and wait for key/DOM conditions. Use a fault hook or the VM adapter to inject a late key or failing storage call exactly at the boundary. Avoid wall-clock sleeps, random stress as the only race test, and mocking `crypto` in the native multi-tab test. [Playwright Clock](https://playwright.dev/docs/api/class-clock)
- **Local and CI.** Add a locked test-only npm manifest and a minimal Node loopback static server supporting a repository-style path. Proposed commands are `npm ci`, `npx playwright install chromium`, and `npm test`. Browser installation may require a one-time download. The suite itself uses local files and loopback only. In GitHub Actions, run Node and Chromium checks on pull requests and pushes to `main`, with a fixed supported Node LTS and locked Playwright, and install Chromium and system dependencies. Retain traces on failures. Keep extra engines and mutation exercises opt-in or scheduled after the baseline is stable. [Playwright CI](https://playwright.dev/docs/ci)

## 5. Mutation exercise

After the unmodified baseline passes, apply one named mutation at a time to a disposable copy of the verified tree. Run the listed detector first, then its suite if useful. Record the baseline SHA, mutation ID and exact edit, command, failing assertion or survivor, and reason. Restore the clean copy between cases. Count a mutation as detected only when a relevant assertion fails. A startup error, timeout, or unrelated failure does not count. A survivor needs a stronger test or a documented explanation that the mutation is equivalent or outside the approved behavior. Fault injection during an ordinary persistence test is separate from deliberately modifying production code.

|---|---|---|
| M01 | Raise the deck cutoff from 100 to 104, or include factor 10 | A01 reports missing 102 and 104, or extra products and factor pairs |
| M02 | Drop 9 × 16 from the 144 answer set or admit 12 × 12 | A01 sees the wrong pair set. L01 rejects a legitimate pair or wrongly accepts the non-deck square |

| M05 | Break wraparound at the last Easy starting position | A04 reports the wrong sequence or missing matches. G06 misses the expected next label |
| M06 | Group a Fog reveal wave with different final digits or reveal after every success | A05 rejects mixed endings. G07 detects premature visibility |
| M07 | Charge a mismatch to the second card | G01 detects the wrong review fact. L04 detects a wrong Fog-derived weak prompt if mutated there |
| M08 | Use a global matched counter for both Easy sections or allow a cross-section miss | G05 detects misaligned rows or incorrect feedback/score |
| M09 | Skip resetting the current recall scores when replaying Easy | G06 reports retained recall counts or an incorrect summary |

## 6. Coverage gaps and limitations

| Area | Initial coverage | Residual gap |
|---|---|---|
| Fact universe and dealing | Exhaustive deck and Easy membership, all public size and length options, fixed random seeds for Classic and Fog | Seeds are samples of permutations. No promise about shuffle fairness or visual positions across runs |
| State transitions | Representative complete, partial, reset, pause, recall, and replay journeys in both games | A complete cross-product of browser, screen size, input modality, and state is intentionally outside initial scope |
| Persistence | In-memory fault injection plus native multi-tab Chromium, lock barriers, recovery and replay | Browser storage eviction, hard OS/process failure, quotas, private browsing, file origins, and lock-free concurrent writes require separate characterization. Tests cannot promise durability beyond successful staging and available storage |
| Accessibility and sound | Named controls, keyboard paths, disabled states, focus, touch, and optional audio routing | Manual screen-reader and device checks remain necessary. A stub proves scheduling and mute routing, not audible output or platform autoplay behavior |
| Deployment | Loopback site under a repository-style subpath | GitHub Pages propagation, cached assets, and link reachability on the public deployment are outside the local suite |
| Learning outcomes | Rules for exposure, recall, review, and retirement | Software tests cannot establish that either game improves multiplication fluency. That needs a separate study |

Additional engines and device checks are desirable follow-ups. Code coverage may help locate unexercised high-risk branches. It is neither a target percentage nor a substitute for invariant and mutation checks.
